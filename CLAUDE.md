# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Agent MCR (Agent Mission Control Room) is a local harness for coding-agent sessions, built on MDViewer. The harness architecture, its signed decisions and the delivery sequence are in `docs/AGENT_HARNESS_DESIGN.md`. Read it before changing harness code. `upstream` is `lambda-house/mdviewer-mj`; viewer fixes are merged from there.

The window has two surfaces (Tauri 2.0, React 19, TypeScript). Sessions holds Live (hosted terminals) and Journal (search in the index of past sessions). Documents shows the agents' Markdown and nothing else: instructions, rules, memory, plans, skills, agents and commands, from the agents' own folders and from the folders their sessions work in, with the Markdown reader (Shiki, Mermaid, tabs, table of contents, find, editor). The general file tree, text search across folders, history, saved workspaces, Open File/Folder, drag and drop and "Open with" are removed: do not bring them back.

## Build Commands

```bash
npm install              # Install dependencies
npm run dev              # Start Vite dev server (port 1420)
npm run tauri dev        # Run full Tauri desktop app in dev mode
npm run build            # TypeScript check + Vite build
npm test                 # Frontend unit tests (Vitest)
npm run build:app        # Build Agent MCR.app (release, ad-hoc signed)
npm run build:win        # Build a per-user Windows NSIS installer
```

Windows requires the MSVC Rust toolchain, C++ build tools and WebView2. From macOS, the Windows compile gate is `PATH="/opt/homebrew/opt/llvm/bin:$PATH" cargo xwin clippy --target x86_64-pc-windows-msvc --all-targets -- -D warnings` in `src-tauri`. The full local gate also runs `npm run build`, `npm test`, `cargo clippy --all-targets -- -D warnings` and `cargo test`; frontend-only and Rust-only changes run their respective checks, while merges run the full gate. CI runs Linux and Windows jobs. Cross-compilation does not run Windows tests.

Frontend unit tests are Vitest files next to the code (`src/utils/*.test.ts`; DOM tests declare `// @vitest-environment happy-dom`). There is no linter. The Rust backend has unit tests: `cd src-tauri && cargo test`.

## Architecture

### Frontend (src/)

- **State Management**: Zustand store in `src/store/index.ts` manages all app state with localStorage persistence
  - Key constants: `MAX_RECENT_CLOSED = 10`, `MIN_ZOOM = 50`, `MAX_ZOOM = 1600` (no tab limit)
  - State includes: file tree, documents/tabs, UI panels, zoom level (document `zoom` plus per-panel `panelZoom`)

- **Components** (`src/components/`):
  - `App.tsx` - Main shell; its key handler runs the commands of `utils/commands.ts`
  - `MainMenu.tsx` - Toolbar menu (top left): every command, grouped, with its shortcut
  - `DocumentPanel.tsx` - Center markdown renderer with ErrorBoundary. Scroll positions per document are anchored to the block at the top of the view (`utils/scrollAnchor.ts`), so late Mermaid output doesn't move the restored text
  - `TabBar.tsx` - Tab strip: preview tab, context menu, back/forward, overflow scrolling
  - `TocSidebar.tsx` - Right sidebar table of contents
  - `AgentPanel.tsx` - The left panel of Documents: agent documents by session folder, then the agents' own
  - `FindBar.tsx` - Ctrl+F find in document (CSS Custom Highlight API; highlights are changed in place, WebKitGTK doesn't repaint replaced ones). A jump and the scroll restore both use `utils/scrollHold.ts` to keep their offset while late output changes the layout
  - `Editor.tsx` - CodeMirror 6 source editor (Ctrl+E), lazy-loaded; per-document state lives in `utils/editorRegistry.ts`, saving in `utils/save.ts`
  - `Toolbar.tsx` - Top bar with search, zoom, theme controls
  - Window chrome (MCR-138): on macOS the main window has an overlay title bar (`src-tauri/tauri.macos.conf.json`: `titleBarStyle: Overlay`, `hiddenTitle`, `trafficLightPosition`; it replaces the window list of `tauri.conf.json` whole, and a Rust test keeps both windows the same apart from those keys). The top row of each workspace (`.toolbar`, `.sc-topbar`) takes `topRowProps(useTitleBar())` from `utils/windowChrome.ts`: 88 px left for the lights (`TRAFFIC_LIGHT_INSET`; the lights at x 14, y 21 centre on the 39 px row: AppKit puts their centre at y − 2, MCR-145), `data-tauri-drag-region="deep"` (drag, double-click zoom), neither in full screen. A part of the row that reacts to the pointer without being a button gets `NO_DRAG`; `utils/dragRegion.testing.ts` copies Tauri's drag rule for the tests. `start_dragging` is allowed by the macOS-only capability `macos-window-chrome.json`. Windows, Linux and the memory reader windows keep native decorations and get no attributes
  - `ConfirmDialog.tsx` - Modal question; buttons in the platform's order (`utils/platform.ts`). `SaveAllDialog.tsx` uses it
  - `Resizer.tsx` - Panel separators: drag to resize, drag to the edge or double-click to hide/show
  - `StatusBar.tsx` - Bottom status bar (auto-hides)

- **Hooks** (`src/hooks/`): `useSmoothWheelScroll` - velocity-based wheel scrolling shared by the document, file panel and TOC

- **Commands** (`src/utils/commands.ts`): `buildMenu` is the one list of commands (label, shortcut, `enabled`/`checked`, `run`). The menu renders it and the key handler in `App.tsx` matches key presses against it, so a new command or shortcut goes there, not into either of them. `run` must be safe when `enabled` is false (shortcuts don't check it)

- **Markdown Processing** (`src/utils/markdown.ts`):
  - markdown-it with `html: false` (raw HTML is escaped; every custom renderer rule must escape what it emits with `escapeHtml`)
  - Shiki for syntax highlighting (15+ languages)
  - Mermaid for diagrams with unique ID generation per render
  - HeadingIdGenerator for automatic anchor links
  - `renderFile` dispatches by type (`getFileKind` in `utils/files.ts`): markdown, fb2 (converted via `utils/fb2.ts`), code (one highlighted fence), plain text
  - Block elements carry `data-line` (0-based source line, frontmatter included) to map search results to the rendered DOM

### Backend (src-tauri/)

Rust backend provides Tauri commands:
- `read_file` / `write_file` - File I/O; `read_file` decodes UTF-16 BOM and XML-declared encodings, `write_file` encodes back the same way (refuses unknown encodings) and replaces the file atomically (temp file + rename, `atomic_write`)
- `pick_directory` / `export_file` - Native folder picker (Live: a folder to start sessions in) and save dialog, opened from Rust (the JS dialog plugin isn't exposed)
- `get_file_info` - File metadata
- `open_external` - Opens http/https/mailto links in the default browser (opener plugin, Rust-side only)
- `localfile://` protocol - Serves images referenced by documents (`convertFileSrc(path, 'localfile')` in the frontend)

Security: an allowlist (`Access` / `AccessState` in main.rs, persisted to `access.json` in the config dir). Paths are added only from Rust on user actions: the folder picker (Live). Nothing is granted for dropped files, command-line paths or files handed over by the system, and there is no carry-over of an older session. Session folders (`Access.session_folders`, not saved) are found by `session_folders` in Rust at every `agent_workspace` scan: the folders of sessions hosted now (asked from a harness service that already runs), the folders added in Live, and the folders of indexed sessions of the last 30 days when the Sessions workspace is on; the home folder and everything above it are left out, at most 40. While the agent workspace is on, `Access::is_agent_file` lets `can_open`/`can_stat` pass the agents' own documents and, inside a session folder, only what `agent::is_project_agent_file` names (never the folder's other Markdown, listings or images). `AgentEntry.folder` says which session folder an entry belongs to (for a Claude memory: the project it is about); `AgentPanel.tsx` groups by it through `agentFolders` in `utils/agent.ts`, nearest folder first, and lists the rest under All folders. Every command resolves its path to a `Target` (as named, and canonicalized with `dunce`) and checks it with `AccessState::check(target, Use::...)`: documents need to be an opened file or a viewable file inside an opened folder, listing/watching needs an opened folder, `localfile://` serves only images. A symlink inside an opened folder passes when its real target fits the use (`Use::fits_target`): Markdown and images only, never other text files; paths with `..` only count as their real location. Never grant access to an arbitrary path passed from the webview. `follow_local_link` grants after the user confirms a native dialog; session memory opening grants only a Markdown file revalidated against the backend memory catalog under separate session and memory consent. 10MB limit for documents, 50MB for images. CSP in `tauri.conf.json`. A navigation guard plugin (`navigation_guard`) blocks any navigation away from the app's own pages; document link clicks are handled in `App.tsx` (anchors, `openExternal`, local files via `followLocalLink` then `openPath`). There is no updater: the app never looks for or installs a new version of itself, and its only network requests are images the user allowed. Do not add one without an owner decision (MCR-24). Remote images render as `span.remote-image` placeholders; `MarkdownViewer` swaps them in with `loadRemoteImages` when the `loadRemoteImages` setting or the per-document "Load images" allows it. Agent workspace (`src-tauri/src/agent.rs`, `AgentPanel.tsx`, `utils/agent.ts`): turned on by `enable_agent_workspace` after a native dialog, stored as `agent_workspace` in `access.json`. While on, `Access::can_open`/`can_stat` also allow `agent::is_agent_document` (markdown in fixed places under `~/.claude`, `~/.codex`, `~/.gemini`; extend `classify_rel` and its test together). Markdown includes Cursor's `.mdc` and `.cursorrules` (`is_markdown_file` / `isMarkdownFile`). `agent::Watch` (started by the `agent_workspace` scan, re-armed on every scan) emits `agent-files-changed`; the frontend debounces it and polls only when `watching` is false. `agent_workspace` scans those plus agent files in opened folders; `mark_read` / `read_snapshot` keep a copy per file in `read-state/` for the "changed since you read it" highlight (`diffContent` + `markChangedBlocks` on `data-line` blocks). Capabilities (`capabilities/default.json`) allow core defaults and window destruction for `main` and `memory-*` readers.

Tests: `cargo test` in `src-tauri` (unit tests at the bottom of main.rs and agent.rs). CI runs clippy, the Rust tests and `npm test`.

### Agent harness (docs/AGENT_HARNESS_DESIGN.md)

Background units and tests: `runner::may_manage` is the one gate for installing, starting, replacing or removing a LaunchAgent. It is false in every test (`cfg!(test)`) and for any folder but the app's own config folder, and `start` refuses to re-register a label that launchd is running. On 2026-11-17 a test that opened a `Harness` in a temporary folder reached `ensure_unit`, which took the installed units for consent, rewrote the real runner's LaunchAgent to a test binary and ended every hosted session. Never weaken that gate, and never add a path to `launchctl` that does not pass it.

`runner.rs` is `agent-mcr --runner` (branches in `main` before Tauri starts): it owns agent PTYs (`portable-pty`), a 4 MB scrollback per session and exit codes, on `runner.sock` in the config dir. It has no policy, MCP or SQLite. Its JSON-lines protocol is versioned (`PROTOCOL`): change it only additively, because the app speaks N−1. `ensure` starts it through the macOS LaunchAgent `cc.lambdahouse.agent-mcr.runner` (plist in `~/Library/LaunchAgents`, rewritten when the executable changes), or as a detached process on Windows, so agents outlive the app. It exits after 10 idle minutes with nothing running. An ended session gives back its pty at the exit, not at `forget` (MCR-151): the wait thread drops the master, tells `exited`, then drops the writer on unix (on Windows the writer goes first, then the master, then `exited`: ClosePseudoConsole with the synchronous writer still open can wait for good before Windows 11 24H2, review 17220), and the reader (`Drained`, its own dup) ends when the output is drained or `EXIT_DRAIN` after the exit (a monotonic clock), even while a left-behind job holds the terminal; a live session holds three ptmx descriptors (master, reader, writer). On unix the writer is the runner's own dup, not portable-pty's, whose destructor waits to write a newline and EOF into the terminal; the master is non-blocking and `Session::type_in` waits for room in `poll` and gives up at the exit, so a full input queue nobody reads cannot hold the end (review 17215); its last look at `Session.ended` and the non-blocking write happen under that marker's lock, which the exit takes to publish it, so no byte is typed once the end is published (review 17220). The runner and the service raise their soft open-files limit at start (`note_open_files`, at most `OPEN_FILES`). `attach` streams raw bytes (scrollback, then live); its reply says `from`, the offset of the first byte in all the session's output (`Output.total`), and `since` starts the replay there while the ring still holds it (`replay_from`, MCR-139; additive, an older runner answers without `from`). A view whose client went away ends within `VIEW_LOOK`, and a view leaves `Output.views` on every way out of `attach` (`Leave`), a failed handshake included, even while the session prints nothing. `watch` streams events, including BEL and OSC 0/2/9/777 found by `Scanner`. `harness_commands.rs` is the app side: the webview only picks a `PROFILES` id (on Unix run as `$login_shell -l -i -c 'exec …'`, D7 permission modes) and a folder it opened, a session directory or home. Output reaches the webview over a raw `Channel`, gathered for `GATHER` (6 ms) and sent as frames of at least `FRAME_MIN` bytes (`frame`: u32 length, bytes, zeros; `unframe` in `utils/harness.ts`; length 0 is the end; the first frame of a view is `start_frame`, length `u32::MAX` and the `from` offset, read by `frameStart`), because Tauri sends a shorter channel message as JavaScript source the web view compiles, and that garbage was most of the web view's weight under load (MCR-139). `terminal_input` writes the key to the runner and returns: the word to the service that the person pressed Enter (`operator_input`) goes through one worker thread (`Told`), which never queues a session twice and takes it off its list before the call starts, so an Enter during a call is told again. Its failure is not a terminal error, and the service writes the store for it only when there is a mark or typed text to take back. Do not put a blocking call to the service back into `terminal_input`. The same command is the witness of the person's unsent line (MCR-85): the service types notices and tasks into idle sessions and never sees a key, so `Draft` follows the keys per session (text and pastes start a line, Enter and Ctrl+C end it, Backspace is counted back only while nothing else happened, Up from an empty box counts as a recalled line until Down was pressed as often, the terminal's own answers to the agent and its focus and mouse reports are no keys, `Draft::report`) and errs towards unsent: Escape does not end a line, because twice it empties the box in Claude Code only. A change goes to the service through `Told` as `operator_draft` (an Enter stays `operator_input`; both carry `draft`, read when the worker calls), and again every `DRAFT_RETELL` while typing goes on; a word about a line that did not reach the service is said again by `retell` until a call succeeds. Pasted images go to the platform cache directory under `agent-mcr/attachments`. Frontend: `LiveWorkspace.tsx` (the Live view in Sessions), `TerminalPane.tsx` (xterm.js), `BoardView.tsx` (the Board view: reports and bulletin notes from the service's `board` op; `note_remove` is the person's only write there) and `utils/harness.ts`. Local builds are the gate (D12).

Socket callers (`peer.rs`): identity comes from the kernel only (Unix: `getpeereid`/`SO_PEERCRED`, `LOCAL_PEERPID`, the peer's program path, its parent chain; Windows: AF_UNIX peer PID, process token SID, executable and parent chain). Never trust an id a caller sends. The runner answers anything but `hello` only to this program outside every live session (`Runner::trusts`). The service: `hello` for all; `hook` is attributed to the session the calling process descends from (`Harness::who` → `Caller`); `agent` as before; every other request needs `Caller::Outside` and this program; `supervise` is for the Supervisor session, and for outside callers only while `Store.outside_supervisors` is on (`settings` op, set through `harness_outside_supervisors` after a native dialog). These checks fail closed and are not a wall between same-user programs; don't describe them as one. The Supervisor's pre-approved tools exclude `terminal_write` (`claude_settings`), so Claude Code asks the operator at each call; `Adapter::asks_before_terminal_write` says that of an agent kind (Claude only), and `allows_terminal_write` lets only such a hosted Supervisor call the tool, over MCP, never through the CLI and never an outside agent. A caller that would be refused is not listed the tool either (`without_terminal_write` on its `tools/list` answer; owner's decision of 2026-11-18, MCR-76). Supervisor tools refuse tasks for shell sessions; keep any new tool that can run a command out of the pre-approved list. Supervisor tasks and anything `deliver` types into an agent must pass `plain_prompt` (no leading `!`, `#` or `/`). The inbox notice typed into a session carries no sender name: a session titles itself. On Unix, non-POSIX login shells (fish) get `/bin/zsh` for agent command lines (`argv_for`); state and logs are 0600. On Windows, `ipc::private_dir` requires a protected user-only DACL, and the config directory is `%LOCALAPPDATA%\agent-mcr`. Windows agents use `cmd.exe` and validated arguments via `AMCR_LAUNCH`; the shell profile uses PowerShell. Free-text first tasks are typed when the agent is ready; unsupported launch characters are rejected. On all platforms, pasted images are removed after two weeks.

What a program says of itself (MCR-115): the runner's `Scanner` hands every OSC body to `program.rs` (pure), which reads OSC 7501 program status (spec rev 0.4: a report is discarded whole when it breaks a limit, its base64 does not decode or its text holds a control character; malformed pairs and unknown keys are skipped; the whole sequence, OSC through ST, at most 4096 bytes, and one that ran past `MAX_OSC` is never read as a report), OSC 133 prompt marks and OSC 9;4 progress (no longer taken for a notification). The runner keeps them per session in `Info.program` (records per id as the spec says: `clear` takes a subtree, working and blocked go at OSC 133 A and at the exit, RIS empties it, at most `MAX_RECORDS` with the least recently updated going first; direction overrides and isolates are taken out of title and msg), in memory only and never in a store, message, report or log; the service passes it through `sessions` and the app shows it as the program's word (`programHint`, `ProgramLine`: "program" and the name it gives itself, in plain weight, because the bold name in a row is a session's and a program may call itself Supervisor, then "reports", its text, a bar for a percent; in the Live row and the pane title), never as a state: the hooks' state and dot stay, and where they disagree the report is struck through. Any output can print these sequences, a file shown in the terminal too, so nothing may take them for the agent's or the owner's word: they set no state, attention, draft or `operator_sent`, and type nothing. A feature query (`7501;?`) is a runner event `program_query` (at most one a second per session); the service answers with the fixed `QUERY_REPLY` only while `Store.program_query` is on (off by default; `harness_program_query` after a native dialog, "Answer program status queries" in Settings → Harnesses), only in a plain terminal of a profile this build knows (`agents::plain_terminal`, `Adapter::is_plain_terminal`: the shell; not `!is_agent`, which would let Antigravity, OpenCode and Pi through, and not an unknown profile, which may be an agent of a later build). In an agent's terminal the program is the agent's own screen, which never asks: a query is output it drew, and an answer would stay in its input box as a line nobody knows of, sent with the next Enter, never while the operator's line is `held`, and under the writer's lock, taken with `try_lock` because this runs on the thread that reads the runner's events: while someone writes, the query is not answered (`answers_program_query`). The parser is runner code: it is live only after a runner restart, and an older runner simply has no `program`. Not built: the hint on the supervisor MCP (with MCR-113), and OSC 133 as an idle signal for typing tasks, which would let output decide when the harness types.

Background consent: `runner::ensure_unit` starts a unit only when `background.state` in the config dir says `allowed` (`runner::consent`; units installed before the question existed count as allowed once). It is written only after a native dialog (`harness_background_allow`) or by the person's stop (`harness::stop_background`: ends sessions, then the service, then the runner; `stop_unit` lets launchd go of a label only when launchd runs this very process, because another build shares the labels). Never start a unit around this gate, and never set the state from the page or from an agent's request. `agent-mcr --stop-background [--uninstall]` is the same off switch without the app.

`harness.rs` is the harness service, `agent-mcr --harness` on `harness.sock` (macOS LaunchAgent `cc.lambdahouse.agent-mcr.harness`, detached on Windows; same `runner::Unit` start as the runner). It creates sessions (`create`: profile or `resume`), tracks their state, queues tasks and serves the supervisor MCP; `harness-state.json` is its store (SQLite comes with messaging). State comes from the agents' own hooks, passed per launch and never written to the user's agent config: Claude gets `--settings claude-hooks.json` (SessionStart, UserPromptSubmit, PostToolUse, Notification, Stop) and `--session-id`; Codex gets `-c notify=…`. Both call `agent-mcr --harness-hook <event>`, which must stay silent and always succeed. `apply_hook` is the pure state machine: test changes there. Three things no hook reports are handled separately, and each was found by a live run: Claude's start-up questions (`stalled`: quiet and no hook yet → attention), Codex turn ends of other threads (title writer, subagents: only the session's own `thread-id` counts; `hook` asks the transcripts through `top_level_thread` which thread is the person's, because a subagent's turn end taken as the session's leaves it `working` for good and no inbox notice is ever typed), and Codex before its first turn end (a task is typed only when `codex_at_prompt` sees the input box, otherwise it would answer whatever is on screen). A fourth (MCR-71): Codex reports no approval request through `notify`, and nothing at all before its first turn ends, so a Codex executor at a prompt looked `working`; Claude Code is created as `precise` and says nothing before its questions at start are answered. `Harness::look` (every `title` event of the runner and the three-second timer) is the fallback. It asks `Adapter::title_asks` (Codex: the title is exactly "Action Required" after its glyph), reads the question from the screen once (`Adapter::question`) and raises `permission` attention with `guess: true`. While an agent has reported nothing (`hooked` false) it also reads the screen once it has been quiet for `LOOK_QUIET_MS`, which finds the folder question at start; `Harness.screens` remembers the output time of the last read, because a screen is read once per output time and never on every look: a snapshot is up to 4 MB. `apply_look` is the pure part (`Seen`): a mark is taken back only when it made the session wait, and the session returns to the state it had (`Attention.was`), never blindly to `working`, or an idle session would never get its queued tasks. What Codex announced itself (`Adapter::announces_approval`: the form "Approval requested", not a word in a last message) is taken back by the title only when the title was seen asking while that mark was up (`Harness.titled`); a title that never asks proves nothing and D6 must keep holding. Do not make Codex announce always (`tui.notification_condition`): it then announces every turn end too. `tell_waiting` is the one place that tells about a session that started to wait: the operator's notification and a notice in its supervisor's inbox. A brief carries `stateNote`, and `stateFromHooks` is false, until a running agent has reported. Codex's own hooks (MCR-74): Codex runs a hook only after the person trusted it in Codex (it asks at start, "Hooks need review", and keeps the trusted hash in the person's `config.toml` itself; the hash covers the command, so another program path asks again). The Codex adapter passes `CODEX_HOOKS` with `-c hooks.<Event>=…` only while `Store.codex_hooks` is on (`settings` op, `codexHooks`; off by default; set through `harness_codex_hooks` after a native dialog, the switch is "Use Codex hooks" in Settings → Harnesses, owner's decision of 2026-11-18; no MCP tool sets it; `Store.codex_hooks_seen` keeps the program path under which a hook last reported, so the row says that Codex runs them also after those sessions are forgotten, and asks for trust again only under another path). They all call `--harness-hook codex-hook`; `trim_hook` keeps of an approval request only the command and Codex's reason, cut short. In `apply_hook`: `SessionStart` gives the conversation id and nothing else (it does not make the session idle, so no task is typed on it), `PermissionRequest` raises `permission` attention in Codex's words (not a guess), `UserPromptSubmit` and `PostToolUse` are as Claude Code's. Codex runs the hooks for its subagents too, under the session's own `session_id`, with `agent_id` and the subagent's `transcript_path` added (recorded 2026-11-18, 0.170): a hook with `agent_id` never moves the conversation id or transcript, clears a mark or changes the state; an approval request is kept from any thread. A hook that prints nothing leaves the approval with the person, and trust for hooks passed with `-c` holds for later launches (both seen in the same run). There is no `Stop` hook: the turn end stays with `notify`, which needs no trust, and a turn end reported twice would clear a report as if the operator had answered. The hook prints nothing, so it never decides a request (D6). `Tracked.own_hooks` marks a session whose hooks reported: `look` then raises nothing from its terminal, but a title that stops asking still takes the mark back, because a refused request has no hook. Sessions without trusted hooks keep the MCR-71 fallback. What an agent asks to run is kept in memory only (owner's decision of 2026-11-18): a mark whose text may hold a command line (Codex's `PermissionRequest`, a question read from the screen by `look`, Codex's approval notification) has `Attention.unsaved`; `saved` writes the store without that text (`UNSAVED_PROMPT` stands in, the mark and the `waiting` state stay), and `waiting_notice`, a stored message, points the supervisor to `session_status` instead of quoting it. The text is on the session, in tool results and in the macOS notification. Keep any new mark that can hold a command `unsaved`, and never put its text into a message, a report or a log. Never pass `--dangerously-bypass-hook-trust`: it would also run a project's untrusted hooks. Tasks are typed as a bracketed paste plus Enter when the session is idle, one at a time; the first task goes in argv on Unix and is queued on Windows. Nothing is typed into a session while the person has an unsent line there (MCR-85; on 2026-11-19 an inbox notice was typed three times into the Supervisor's half-written prompt and sent with it): `held` is true while `Tracked.draft` is set and for `DRAFT_QUIET_MS` after a line was emptied without being sent, and `nudge` and `pump` ask it before anything else, so the message stays not notified and the task queued until the timer comes back. A draft has no time limit, so a hold must never be silent: `overview`, `session_status` and `list_peers` carry `held` (`held_info`: since when, and that only the operator ends it), the Live row says `heldNote` when something waits for it, and after `HELD_TELL_MS` `tell_held` tells the operator once per draft (a notification and an `assessment` mark with `HELD_MARK`, which goes with the line) and the session's supervisor in its inbox. Do not add a time limit that types into the line after all. A key pressed while the session asks something (`permission` attention) starts no draft: it answers the question, often without Enter. That alone missed a key told before the hook marked the prompt, or at a menu no hook reports, and such a "draft" held every message and task until Enter (MCR-122, a digit that answered Claude Code's permission menu). So: `check_drafts` on the timer reads, at most every `DRAFT_CHECK_MS`, the screen of a session whose draft has had no word from the app for that long (`Harness.draft_words`, in memory; a word told while the screen is read keeps the hold) and whose adapter can prove an empty input box (`Adapter::empty_input_box`, Claude Code only: Codex shows suggestions in an empty box), and ends the hold on an empty box (`clear_draft`, which keeps `held` for `DRAFT_QUIET_MS` so a key being told lands first). Where the screen cannot tell, a `permission` mark that goes because the agent moved on (`drop_prompt`, `apply_look`) takes a draft begun at most `ANSWER_LEAD_MS` (3 s) before the mark, or after it, as the answer (`answered`); for Claude Code it takes none, so a line typed ahead just before a prompt keeps its hold. Cockpit (epic MCR-94; `cockpit.rs`, first slice MCR-95: schema, store, tools, no panel): `Store.cockpit` holds what hosted sessions publish for the operator (`Track`, `Item`, `Action`), by publisher (`Cockpit.parts`, keyed by session id; the root Supervisor's part has the key `ROOT`, which belongs to the role), so who wrote a track is where it lies and never a field an agent sets. `cockpit.rs` is pure: the service hands in `Facts` (`Store::cockpit_facts`, from the store alone) and `Who` (the calling session by its process; `root` from the runner's `meta.role`). Two layers that are never mixed: published text is validated, stored and shown; what the harness knows is joined at every read (`Cockpit::read`) and never stored, so published text never overrides a fact and a fact never rewrites published text. Derived at read: a session with `permission` attention is an action `answer_prompt` (the prompt's text is not copied), an open `needs_human` report an action `report` unless a published action names its id in `source` (then that one carries `live.reportOpen`), and an item without `waitsOn` shows its owner's first registered wait (`derived: "wait"`). Two more since MCR-118 (the owner missed a session at a question and a placed line waiting for Enter, because "Needs you" depended on someone publishing): the operator's unsent line in an agent's input box that has stood `HELD_SHOW_MS` (`Fact.held`; never in a shell, where `Draft` cannot tell a line from keys for less, vim or htop; an action `held_line` that says to press Enter there if the box is empty, and otherwise to send or delete the line (never Ctrl+C, MCR-122), never for the Supervisor's own session, whose box is under the panel), and a `human` wait past its time (`human_wait`, with what the session registered as its text). The panel ranks such a merged row with the harness's own (`harnessSaw`), at the harness's urgency (`harnessUrgency`: a prompt is `now`, the rest `today`; a publisher's urgency never outranks it), never folds it away, shows the facts as chips (`harnessChips`), and offers no Place or choice while the session is at a prompt (`clickable`; the service would refuse it). A read of the cockpit that takes longer than `READ_TIMEOUT_MS` is an error on the panel, never the last read shown as now, and only the newest read may change what is shown. Agents cannot publish `answer_prompt`, `report`, `held_line` or `human_wait`. Rights (`may_write`, `reach`): any hosted session that runs publishes, with executors or without, and only its own part, in this structure and no other (owner's decision of 2026-11-19: "any session can publish but it must be structured"); a track's `lead` and an action's `where.session` are the caller or a session below it; the Supervisor also gives `order`, adds actions without a track or on another part's track (`trackBy`) and removes (never edits) another part's track or action; without a hosted caller (the app's `cockpit` op, an outside agent with the supervisor tools) everything is read and nothing published. `supervise` routes `cockpit_*` to `cockpit_tool` with the caller, because `tool` knows none. Validation refuses with the place of the first fault and stores nothing: unknown fields, kinds and states, sizes, control characters and direction overrides, session ids that are not tracked or have ended, and per kind only what its later click may use (`typed_word`: `where.session` and a one-line `say` that passes the `plain_prompt` rule; `decision`: options; `secret_step` and `live_check`: `detail`, and a `where.command` that is shown to copy; `external`: an http(s) link without a user part). Four rules from the review of MCR-95, each with a test: the stored types take unknown fields and `cockpit::load` (`Store.cockpit` is read through `cockpit::stored`) turns a document this build cannot read, or one of a later `schema`, into an empty cockpit, because an error there would fail the load of the whole store and `Harness::open` would start empty; the strictness is on what a session sends (`known`, the field lists). A file that cannot be opened at all (rights, an I/O error) may be whole: it is never moved. Then, and when a file cannot be kept aside, `Harness.frozen` stops every write of the store for that run. In every other case the store is written once at start, with the notice. `Store.notice` (`StoreNotice`: part names and entry ids, never stored text, and a parse error only as its kind, line and column, because serde quotes the value) stays until the operator dismisses it in Live (`storeNoticeSeen` on the `settings` op). Raise `STORE_SCHEMA` when a build writes what an earlier one would read wrongly, and add any new part of the store to `read_store`.

A session's end is in the store (MCR-75): `Store::end` sets `Tracked.state` to `exited` (`ENDED`), clears prompt and other transient marks, and closes open waits unless a restart is carrying them to a new id. The report mark survives exit, including a report that was behind a prompt. The Board keeps the report after acknowledgement. It is called for the runner's `exited` event and by `Harness::sessions` for an exit the service did not hear of (it was down or restarting). Before that the store kept an ended, not yet forgotten session with its last state, and a status report listed it among the executors, one as `waiting`. `set_state`, `apply_hook` and `apply_look` leave an ended session alone; `Store::executors` and `executor_lines` are the running ones only, the same set as `overview`, so an ended executor takes no place under `MAX_EXECUTORS`; its `supervisor` stays for the record and authorizes the assigner to read the task result by id. Unread messages and task-result notices from the ended executor remain available in the recipient's inbox. A status report asks `sessions` first.

Supervisors and executors (decision D15, MCR-41): `Tracked.supervisor` is the id of the session a session works for; `Harness::restart` carries it to the new id, and `Store::drop_dangling` (run on every update) makes executors independent when their supervisor is gone. Nothing restores a relation by itself. `Store::bind` is the one place that sets it: no self, no circle, at most `MAX_DEPTH` levels and `MAX_EXECUTORS` per session. A relation is made by the operator (`harness_spawn` with `supervisor`, `harness_bind` after a native dialog), by the root Supervisor for a session it creates (`session_create(supervisor)`) or by a hosted agent for itself (`executor_create`, in its own folder or below). Never hold the store's lock in an `if let` or `match` scrutinee around a call to `update`: the mutex is not re-entrant and the service hangs. The task tools of the mcr server (`task_assign`, `task_status`, `task_wait`, `session_status`, `session_result`, `terminal_read`) first check `Harness::mine` / `Store::under`: a session reaches its executors and theirs, never another session; there is no `terminal_write` for it, and D6 holds. `Task.by` names the assigning session and is set from the caller's process, never from tool arguments; `tell_assigners` puts the outcome in its inbox, and `report` also posts to the supervisor's inbox. Waits (MCR-41, part two): `Store.waits` holds what sessions registered with `wait_register`; `Harness::escalate_waits`, on the service's three-second timer, tells the session's supervisor (or the root Supervisor) when a wait runs past its time and, after as long again, raises attention for the operator; `wait_resolve` is for a supervisor above the waiting session. `Tracked.created_by` is set only by `executor_create`, and `executor_end` ends only such an executor that is idle, still works for the caller and has no executors of its own (MCR-46). In the list, `relationRows` (`utils/harness.ts`) orders one folder as trees; an executor whose supervisor is in another folder stays in its own folder and names it.

Slack connector (`slack.rs`, decision D14, epic MCR-26; design and its "What is built" table in `docs/AGENT_HARNESS_DESIGN.md`): part of the harness service, never of the runner or the app. It holds one Socket Mode connection (`tungstenite`) and calls Slack's Web API with form POSTs (`ureq`). The bot and app-level tokens live only in the macOS Keychain (`Vault`, service `cc.lambdahouse.agent-mcr.slack`): never put them in `slack-state.json`, a status, a tool result, a log line or the audit. `slack-state.json` holds the connection record, channel policies, received messages, posts and the audit; every change is written before it is acted on. Invariants, each with a test in `slack.rs`: a message reaches a session only from a sender on the channel's list, once, as inbox data (`Message.slack`), never typed into a terminal; a post is sent only in state `approved` with `allowed_by` set, by the channel's policy, the app (`slack_decide`) or a Slack button pressed by the recorded operator for the stored text hash; a post is sent at most once (`sending` → `unknown` → looked up in the channel's history, never retried); agent text is escaped and shown in `plain_text` blocks or with `verbatim: true`, so it mentions nobody. Only `control` (the app) changes policies or decides; the supervisor has `slack_status` and nothing else. Approval in Slack is off at connect (owner's decision of 2026-11-18): only the operator's switch (`set_slack_approval`, after a native dialog) turns it on, and a stored connection keeps its setting. The app's commands (`slack_*` in `harness_commands.rs`) ask in a native dialog before connecting, before a policy that posts without approval, and before another person's messages may reach an agent. `Slack` talks to the rest of the service through the `Host` trait and to Slack through `Web`, both faked in tests; `SlackView.tsx` is the panel. The app manifest for the Slack app is `docs/slack-app-manifest.yaml`.

Memory server (`memory.rs`, decision D16, MCR-49; "Memory server" in `docs/AGENT_HARNESS_DESIGN.md`): part of the harness service, never of the runner or the app. Every Claude and Codex launch gets a second MCP server, `mcr-memory` (`agent-mcr --memory-mcp`, the same `bridge` as `mcr`, socket op `memory`; `memory::SERVER` is the name in `claude_mcp`, in the Codex `-c mcp_servers.mcr-memory.*` words of both launch paths (`command_line` and `windows_args`) and in the `mcp__mcr-memory` allow rule; do not shorten it to `memory`, a common name for a person's own server that ours would then replace or share the pre-approval with: owner's decision of 2026-11-19, MCR-80; the flag, the socket op and the Keychain service keep the plain word). `Memory` is the router: `tools/list` and `tools/call` go unchanged to a `Backend` (`RemoteMcp`, MCP over streamable HTTP with `ureq`; the local memory will be a second one), and a call that leaves `memory` out gets `DEFAULT_MEMORY` where the tool's schema takes it. `Link` is the single holder of the sign-in: the OAuth client id, the authorization server's addresses (`meta`), the refresh token and the access token live only in the system's secret store (`vault.rs`: the macOS Keychain, on Windows the Credential Manager; service `cc.lambdahouse.agent-mcr.memory`; `Vault` and `Keychain` are shared with Slack, each with its own service name). Never put them in `memory-state.json`, a status, a tool result, a log line, or a session's configuration or environment; and never read from that file where a token is sent, because any process of the person can write it (`Link::meta` reads the vault and applies `Meta::sound`). Invariants, each with a test in `memory.rs` against a fake server on loopback: a refresh runs under one mutex and keeps the rotated refresh token first, because a spent one revokes the grant; a refresh refused with `invalid_grant` signs out (`signed_out`) and is not retried, any other refusal keeps the sign-in; a renewal is never given a shorter timeout to fit a call (`RemoteMcp::token` lets it run on beside a call that is short of time); nothing waits for a call that is under way: `Link.epoch` counts sign-ins and their ends, a renewal, a code exchange, the tool list and the MCP session carry the number they started under, and `Link.keeping` (never held across the network) makes keeping or removing tokens one step with the look at that number, so what arrives for a sign-in that was called off is revoked and not kept; do not make `disconnect` take `refreshing`, the tool list or the session mutex again, it deadlocked and outlasted the control client's ten seconds; a call is refused when its tool's schema cannot be had, so the default memory never fails open; the callback must carry the sent `state` and the issuer's `iss`; token, registration and revocation addresses must be the issuer's own, https only (loopback http only under `cfg(test)`), with no redirects followed; a memory that is not connected still answers `initialize` and says so; a caller that is no hosted session gets no tools; `initialize` waits at most `AT_START` for the memory service. Only `control` (the app) connects and disconnects: `memory_connect` and `memory_disconnect` in `harness_commands.rs` ask in a native dialog and open the browser from Rust, and no agent or supervisor tool changes the connection. `Memory::open` takes an in-memory vault under `cfg(test)`: no test may reach the Keychain, and no test calls the `memory_connect` control op, which would ask the real service. The session id is logged with the tool name and not sent on. Not built: several memories, an allow-list, pinned descriptions, per-session identity, the command form (`--harness-tool`) for memory.

### Unsent lines across app relaunches

MCR-148 keeps existing holds when the app opens. The runner's input box survives the app, including text the operator typed and lines placed by the cockpit. An app process uses a generation from the host's monotonic clock. The service keeps the latest generation in memory and rejects late draft updates and hold dismissals from older app processes. Other requests use their own validity checks. Cockpit actions use their action stamp and the target session's current state, with the session writer protecting placement.

Only the app whose local key count started a hold may clear it by counting back to zero. A cockpit placement gives no app ownership of the hold. The hold is saved with the session, but its generation stays in memory because monotonic ticks identify an app only within a host boot. Saving the generation safely would also require a boot identity. After a service restart, the operator can press Enter to clear the inherited hold. The existing quiet-screen check also clears a hold when the adapter can prove the box is empty. The cockpit's **Clear hold for empty input** records the operator's check for the displayed hold and writes no bytes to the terminal.

`TerminalPane` keeps one pending plain Enter while its visible `TerminalView` attaches if no earlier key in the sequence was dropped. Writes to an attached view run in order. A dropped Enter ends the lost sequence, so the operator can retype and submit. The pane shows a notice when attach or replay drops keys. If a detached view rejects a plain Enter after all earlier writes succeeded, the pane reattaches through the same replay path and tries that byte once more if the old view dropped no further keys. Leaving the pane cancels writes still queued for its handle, including any pending Enter. The keyboard regression tests the pinned xterm.js version in the browser terminal.

### Sessions workspace

`SessionWorkspace.tsx` is entered from the toolbar. `utils/sessions.ts` defines its IPC contract and pure accounting/search helpers. The Journal polls `sessions_journal_since` with its stamp every five seconds (MCR-141). It gets changed session summaries and their positions, removed sources, or an empty reply for the same stamp. The service retains four revisions of source paths and hashes, and sends a full snapshot to a web view without a retained stamp. Older web views can still call `sessions_snapshot_since` or `sessions_snapshot`. Live asks `sessions_pick` for its hosted conversations (summarised alone by `scan_where`) and polls the Journal index every `LIVE_SNAPSHOT_MS` for earlier session titles. `src-tauri/src/sessions.rs` is the incremental Codex/Claude JSONL index, backed by `session_db.rs` (SQLx SQLite) and versioned checkpoints plus paged events. All database work runs on blocking workers. Checkpoints and events commit atomically. The in-memory index keeps summaries and scan metadata. SQLite holds the event tails and parser maps, which load on demand. Usage deduplication survives restart. Do not discard history when directory enumeration fails. `session_memory.rs` discovers fixed memory locations and revalidates each read; `Access.session_memories` is a separate native grant. Human forks are not child agents. Directory history, role and last-activity filters are defined in `utils/sessions.ts`; `session_commands.rs` holds the opt-in access gate. There is no control of sessions outside the harness: the "direct" tab and `session_control` (Codex's own daemon socket) are removed, and the harness is the only way to type into an agent. The app holds no third-party credentials and fetches nothing from outside services (MCR-24): ticket keys found in transcripts are shown as text; do not add a network client for them. `Access.session_workspace` is independent of `agent_workspace`. Do not grant general document reads for transcripts. Usage records must be deduplicated; cache/reasoning are subsets of input/output, not extra totals. Summaries exclude activity bodies, and details load on selection. Status inferred from files must not be presented as verified process liveness. Tests cover parser accounting, partial/truncated files, hierarchy and the UI access/control paths. `examples/session_snapshot.rs` extracts real local metadata using the same index.

Memory reader windows use a validated `memoryDocument` URL and isolated, read-only inherited preferences. They do not overwrite the main workspace, own its watchers or consume its launch paths. Native menu events target the focused window.

### Session analysis MCP

`session_analysis.rs` is the bounded read-only query layer; `session_mcp.rs` implements MCP lifecycle, the app-owned Unix-domain socket (also on Windows) and the `--mcp` stdio bridge. The bridge branch in `main` must run before AppKit/Tauri initialization and never open SQLite. `session_analysis_commands.rs` owns the per-process native-confirmed grant and background ingestion using the same `SessionState.index` as the UI. Revocation closes connected sockets; keep grant→index lock order. `SessionAgentAccess.tsx` shows scope, clients, query audit and evidence navigation. Never infer inner exec execution, skill success, historical definition versions or per-tool tokens from references. `examples/analysis_host.rs` and `scripts/validate-session-mcp.mjs` exercise the production query/transport with the official MCP client SDK and explicit fixture paths. See `docs/SESSION_ANALYSIS_MCP.md` for semantics and remaining limits.

TypeScript path alias `@/*` maps to `src/*` (configured in tsconfig.json and vite.config.ts).

## Configuration

There is no config file. UI settings, folders, tabs and workspaces live in localStorage (Zustand persist). The backend's config dir (`dirs::config_dir()/agent-mcr`) holds `access.json`, `history/history.md`, `read-state/` (agent workspace), and `sessions/index.sqlite` with its SQLite sidecars. Revoking session access clears the SQLite index and disables memory access.

## Key Patterns

- React functional components with hooks (no class components except ErrorBoundary)
- CSS custom properties for theming: dark by default, light overrides under `:root[data-theme='light']`; Shiki emits both themes as `--shiki-dark` / `--shiki-light` variables
- Zustand actions return `{ success: boolean; error?: string }` for operations that can fail
- Scroll handlers debounced at 50ms
- Mermaid renders lazily with strict security level
