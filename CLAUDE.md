# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Agent MCR (Agent Mission Control Room) is a local harness for coding-agent sessions, built on MDViewer. The harness architecture, its signed decisions and the delivery sequence are in `docs/AGENT_HARNESS_DESIGN.md`. Read it before changing harness code. `upstream` is `lambda-house/mdviewer-mj`; viewer fixes are merged from there.

The window has two surfaces (Tauri 2.0, React 19, TypeScript). Sessions holds Live (hosted terminals) and Journal (search in the index of past sessions). Documents shows the agents' Markdown and nothing else: instructions, rules, memory, plans, skills, agents and commands, from the agents' own folders and from the folders their sessions work in, with the Markdown reader (Shiki, Mermaid, tabs, table of contents, find, editor). The general file tree, text search across folders, history, saved workspaces, Open File/Folder, drag and drop and "Open with" are removed: do not bring them back.

## Build Commands

```bash
npm install              # Install dependencies
npm run dev              # Start Vite dev server (port 1420)
npm run tauri dev        # Run full Tauri desktop app in dev mode
npm run build            # TypeScript check + Vite build
npm test                 # Frontend unit tests (Vitest)
npm run build:app        # Build Agent MCR.app (release, ad-hoc signed)
```

Frontend unit tests are Vitest files next to the code (`src/utils/*.test.ts`; DOM tests declare `// @vitest-environment happy-dom`). There is no linter. The Rust backend has unit tests: `cd src-tauri && cargo test`.

## Architecture

### Frontend (src/)

- **State Management**: Zustand store in `src/store/index.ts` manages all app state with localStorage persistence
  - Key constants: `MAX_RECENT_CLOSED = 10`, `MIN_ZOOM = 50`, `MAX_ZOOM = 1600` (no tab limit)
  - State includes: file tree, documents/tabs, UI panels, zoom level (document `zoom` plus per-panel `panelZoom`)

- **Components** (`src/components/`):
  - `App.tsx` - Main shell; its key handler runs the commands of `utils/commands.ts`
  - `MainMenu.tsx` - Toolbar menu (top left): every command, grouped, with its shortcut
  - `DocumentPanel.tsx` - Center markdown renderer with ErrorBoundary. Scroll positions per document are anchored to the block at the top of the view (`utils/scrollAnchor.ts`), so late Mermaid output doesn't move the restored text
  - `TabBar.tsx` - Tab strip: preview tab, context menu, back/forward, overflow scrolling
  - `TocSidebar.tsx` - Right sidebar table of contents
  - `AgentPanel.tsx` - The left panel of Documents: agent documents by session folder, then the agents' own
  - `FindBar.tsx` - Ctrl+F find in document (CSS Custom Highlight API; highlights are changed in place, WebKitGTK doesn't repaint replaced ones). A jump and the scroll restore both use `utils/scrollHold.ts` to keep their offset while late output changes the layout
  - `Editor.tsx` - CodeMirror 6 source editor (Ctrl+E), lazy-loaded; per-document state lives in `utils/editorRegistry.ts`, saving in `utils/save.ts`
  - `Toolbar.tsx` - Top bar with search, zoom, theme controls
  - `ConfirmDialog.tsx` - Modal question; buttons in the platform's order (`utils/platform.ts`). `SaveAllDialog.tsx` uses it
  - `Resizer.tsx` - Panel separators: drag to resize, drag to the edge or double-click to hide/show
  - `StatusBar.tsx` - Bottom status bar (auto-hides)

- **Hooks** (`src/hooks/`): `useSmoothWheelScroll` - velocity-based wheel scrolling shared by the document, file panel and TOC

- **Commands** (`src/utils/commands.ts`): `buildMenu` is the one list of commands (label, shortcut, `enabled`/`checked`, `run`). The menu renders it and the key handler in `App.tsx` matches key presses against it, so a new command or shortcut goes there, not into either of them. `run` must be safe when `enabled` is false (shortcuts don't check it)

- **Markdown Processing** (`src/utils/markdown.ts`):
  - markdown-it with `html: false` (raw HTML is escaped; every custom renderer rule must escape what it emits with `escapeHtml`)
  - Shiki for syntax highlighting (15+ languages)
  - Mermaid for diagrams with unique ID generation per render
  - HeadingIdGenerator for automatic anchor links
  - `renderFile` dispatches by type (`getFileKind` in `utils/files.ts`): markdown, fb2 (converted via `utils/fb2.ts`), code (one highlighted fence), plain text
  - Block elements carry `data-line` (0-based source line, frontmatter included) to map search results to the rendered DOM

### Backend (src-tauri/)

Rust backend provides Tauri commands:
- `read_file` / `write_file` - File I/O; `read_file` decodes UTF-16 BOM and XML-declared encodings, `write_file` encodes back the same way (refuses unknown encodings) and replaces the file atomically (temp file + rename, `atomic_write`)
- `pick_directory` / `export_file` - Native folder picker (Live: a folder to start sessions in) and save dialog, opened from Rust (the JS dialog plugin isn't exposed)
- `get_file_info` - File metadata
- `open_external` - Opens http/https/mailto links in the default browser (opener plugin, Rust-side only)
- `localfile://` protocol - Serves images referenced by documents (`convertFileSrc(path, 'localfile')` in the frontend)

Security: an allowlist (`Access` / `AccessState` in main.rs, persisted to `access.json` in the config dir). Paths are added only from Rust on user actions: the folder picker (Live). Nothing is granted for dropped files, command-line paths or files handed over by the system, and there is no carry-over of an older session. Session folders (`Access.session_folders`, not saved) are found by `session_folders` in Rust at every `agent_workspace` scan: the folders of sessions hosted now (asked from a harness service that already runs), the folders added in Live, and the folders of indexed sessions of the last 30 days when the Sessions workspace is on; the home folder and everything above it are left out, at most 40. While the agent workspace is on, `Access::is_agent_file` lets `can_open`/`can_stat` pass the agents' own documents and, inside a session folder, only what `agent::is_project_agent_file` names (never the folder's other Markdown, listings or images). `AgentEntry.folder` says which session folder an entry belongs to (for a Claude memory: the project it is about); `AgentPanel.tsx` groups by it through `agentFolders` in `utils/agent.ts`, nearest folder first, and lists the rest under All folders. Every command resolves its path to a `Target` (as named, and canonicalized with `dunce`) and checks it with `AccessState::check(target, Use::...)`: documents need to be an opened file or a viewable file inside an opened folder, listing/watching needs an opened folder, `localfile://` serves only images. A symlink inside an opened folder passes when its real target fits the use (`Use::fits_target`): Markdown and images only, never other text files; paths with `..` only count as their real location. Never grant access to an arbitrary path passed from the webview. `follow_local_link` grants after the user confirms a native dialog; session memory opening grants only a Markdown file revalidated against the backend memory catalog under separate session and memory consent. 10MB limit for documents, 50MB for images. CSP in `tauri.conf.json`. A navigation guard plugin (`navigation_guard`) blocks any navigation away from the app's own pages; document link clicks are handled in `App.tsx` (anchors, `openExternal`, local files via `followLocalLink` then `openPath`). There is no updater: the app never looks for or installs a new version of itself, and its only network requests are images the user allowed. Do not add one without an owner decision (MCR-24). Remote images render as `span.remote-image` placeholders; `MarkdownViewer` swaps them in with `loadRemoteImages` when the `loadRemoteImages` setting or the per-document "Load images" allows it. Agent workspace (`src-tauri/src/agent.rs`, `AgentPanel.tsx`, `utils/agent.ts`): turned on by `enable_agent_workspace` after a native dialog, stored as `agent_workspace` in `access.json`. While on, `Access::can_open`/`can_stat` also allow `agent::is_agent_document` (markdown in fixed places under `~/.claude`, `~/.codex`, `~/.gemini`; extend `classify_rel` and its test together). Markdown includes Cursor's `.mdc` and `.cursorrules` (`is_markdown_file` / `isMarkdownFile`). `agent::Watch` (started by the `agent_workspace` scan, re-armed on every scan) emits `agent-files-changed`; the frontend debounces it and polls only when `watching` is false. `agent_workspace` scans those plus agent files in opened folders; `mark_read` / `read_snapshot` keep a copy per file in `read-state/` for the "changed since you read it" highlight (`diffContent` + `markChangedBlocks` on `data-line` blocks). Capabilities (`capabilities/default.json`) allow core defaults and window destruction for `main` and `memory-*` readers.

Tests: `cargo test` in `src-tauri` (unit tests at the bottom of main.rs and agent.rs). CI runs clippy, the Rust tests and `npm test`.

### Agent harness (docs/AGENT_HARNESS_DESIGN.md)

Background units and tests: `runner::may_manage` is the one gate for installing, starting, replacing or removing a LaunchAgent. It is false in every test (`cfg!(test)`) and for any folder but the app's own config folder, and `start` refuses to re-register a label that launchd is running. On 2026-11-17 a test that opened a `Harness` in a temporary folder reached `ensure_unit`, which took the installed units for consent, rewrote the real runner's LaunchAgent to a test binary and ended every hosted session. Never weaken that gate, and never add a path to `launchctl` that does not pass it.

`runner.rs` is `agent-mcr --runner` (branches in `main` before Tauri starts): it owns agent PTYs (`portable-pty`), a 4 MB scrollback per session and exit codes, on `runner.sock` in the config dir. It has no policy, MCP or SQLite. Its JSON-lines protocol is versioned (`PROTOCOL`): change it only additively, because the app speaks N−1. `ensure` starts it through the LaunchAgent `cc.lambdahouse.agent-mcr.runner` (plist in `~/Library/LaunchAgents`, rewritten when the executable changes), so agents outlive the app. It exits after 10 idle minutes with nothing running. `attach` streams raw bytes (scrollback, then live). `watch` streams events, including BEL and OSC 0/2/9/777 found by `Scanner`. `harness_commands.rs` is the app side: the webview only picks a `PROFILES` id (run as `$login_shell -l -i -c 'exec …'`, D7 permission modes) and a folder it opened, a session directory or home. Output reaches the webview over a raw `Channel`. Pasted images go to `~/Library/Caches/agent-mcr/attachments`. Frontend: `LiveWorkspace.tsx` (the Live view in Sessions), `TerminalPane.tsx` (xterm.js), `BoardView.tsx` (the Board view: reports and bulletin notes from the service's `board` op; `note_remove` is the person's only write there) and `utils/harness.ts`. Local builds are the gate (D12).

Socket callers (`peer.rs`): identity comes from the kernel only (`getpeereid`/`SO_PEERCRED`, `LOCAL_PEERPID`, the peer's program path, its parent chain). Never trust an id a caller sends. The runner answers anything but `hello` only to this program outside every live session (`Runner::trusts`). The service: `hello` for all; `hook` is attributed to the session the calling process descends from (`Harness::who` → `Caller`); `agent` as before; every other request needs `Caller::Outside` and this program; `supervise` is for the Supervisor session, and for outside callers only while `Store.outside_supervisors` is on (`settings` op, set through `harness_outside_supervisors` after a native dialog). These checks fail closed and are not a wall between same-user programs; don't describe them as one. The Supervisor's pre-approved tools exclude `terminal_write` (`claude_settings`), and supervisor tools refuse tasks for shell sessions; keep any new tool that can run a command out of the pre-approved list. Supervisor tasks and anything `deliver` types into an agent must pass `plain_prompt` (no leading `!`, `#` or `/`). The inbox notice typed into a session carries no sender name: a session titles itself. Non-POSIX login shells (fish) get `/bin/zsh` for agent command lines (`argv_for`). State and logs are 0600; pasted images are removed after two weeks.

Background consent: `runner::ensure_unit` starts a unit only when `background.state` in the config dir says `allowed` (`runner::consent`; units installed before the question existed count as allowed once). It is written only after a native dialog (`harness_background_allow`) or by the person's stop (`harness::stop_background`: ends sessions, then the service, then the runner; `stop_unit` lets launchd go of a label only when launchd runs this very process, because another build shares the labels). Never start a unit around this gate, and never set the state from the page or from an agent's request. `agent-mcr --stop-background [--uninstall]` is the same off switch without the app.

`harness.rs` is the harness service, `agent-mcr --harness` on `harness.sock` (LaunchAgent `cc.lambdahouse.agent-mcr.harness`, same `runner::Unit` start as the runner). It creates sessions (`create`: profile or `resume`), tracks their state, queues tasks and serves the supervisor MCP; `harness-state.json` is its store (SQLite comes with messaging). State comes from the agents' own hooks, passed per launch and never written to the user's agent config: Claude gets `--settings claude-hooks.json` (SessionStart, UserPromptSubmit, PostToolUse, Notification, Stop) and `--session-id`; Codex gets `-c notify=…`. Both call `agent-mcr --harness-hook <event>`, which must stay silent and always succeed. `apply_hook` is the pure state machine: test changes there. Three things no hook reports are handled separately, and each was found by a live run: Claude's start-up questions (`stalled`: quiet and no hook yet → attention), Codex turn ends of other threads (title writer, subagents: only the session's own `thread-id` counts; `hook` asks the transcripts through `top_level_thread` which thread is the person's, because a subagent's turn end taken as the session's leaves it `working` for good and no inbox notice is ever typed), and Codex before its first turn end (a task is typed only when `codex_at_prompt` sees the input box, otherwise it would answer whatever is on screen). Tasks are typed as a bracketed paste plus Enter when the session is idle, one at a time; the first task goes in argv. `--supervise` bridges stdio to the supervisor MCP (`supervisor_tools`, root per D5). D6 is enforced in `tool`: `task_assign`, `terminal_write` and `session_interrupt` are refused while a session's attention is `permission`. `terminal_read` renders the runner's `snapshot` through `vt100`. `resumable` / `find_resumable` read ids, folders and times from transcript heads, plus `transcript_summary` (agents.rs) over the first 120 lines: a title (custom title, else the first user message) and a role and scope tags guessed from tool calls. The role is a guess and the UI says so; this text only reaches the webview through `harness_resumable`, behind the Sessions workspace grant. A resume id must match an existing transcript. The app lists and creates sessions through the service and keeps terminal bytes on the runner.

Harness tools between sessions (agent agnostic): every Claude and Codex launch also gets the `mcr` MCP server (`agent-mcr --harness-mcp`; Claude via `--mcp-config claude-mcp.json` and a `mcp__mcr` allow rule in the per-launch settings, Codex via `-c mcp_servers.mcr.*`). Tools in `agent_tools` / `agent_tool`: `whoami`, `list_peers`, `send_message`, `ask`, `reply`, `read_inbox`, `listen`, `set_status`. Reports, notes and roles: `report` (`needs_human` or `done`) is the agent's own word to the operator. `Store::report` records it (`Store.reports`, `reports_list` on the supervisor MCP) and puts it on the session as an `Attention` with `report` set: kind `assessment` for `needs_human`, `notification` for `done`, never over a `permission` prompt. Hooks must not clear it (`drop_prompt` clears only prompts): the tool call's own PostToolUse would. It goes when the operator types into the session (a UserPromptSubmit more than `INJECTED_PROMPT_MS` after the harness last typed there, `Tracked.injected` set in `deliver`; for Codex, which reports no prompts, the first later turn end the harness did not start) or, for `done`, when they select the row (`ack`). `assessment` does not make the supervisor's input refused: that is for `permission` only. The bulletin board is `Store.notes` (`Note`): `bulletin_post` needs `expires_hours` (1 to 336) and takes `until_i_end` (removed at the session's exit) and `scope` (`folder`: the author's folder, matched by `folder_relation` to readers in it, below it or above it; `all`). `bulletin_read` marks notes seen per session; every tool result carries `bulletin` (unseen notes) next to `unread`. Note text is never typed into a terminal or added to a prompt by the harness: a session reads it with the tool, as data. `list_peers` puts sessions of the caller's folder first with `folder` (`same`, `below`, `above`) and `role` (`Tracked.role`, set by `set_status` or the supervisor's `session_create`; the supervisor session shows as `supervisor`). `Tracked.cwd` is kept by `sessions` so notes need no runner call. The app has no view of the board or of past reports yet; the supervisor tools `bulletin_list`, `bulletin_post`, `bulletin_remove` and `reports_list` are the way in. The caller is never trusted to say who it is: `caller` takes the socket's peer pid from the kernel and walks parent pids up to a runner child; anything else gets a server whose tools refuse. Messages live in the store (`Message`, kept for the operator; `messages_list` on the supervisor MCP). Delivery is `nudge`: when the receiver is idle, a fixed notice without the message body is typed into its terminal and the agent calls `read_inbox`; never into a shell, and never while a session waits on a prompt (state `waiting` is not idle). A Stop while a peer still owes a reply to an `ask` leaves the session's task open (`Store::awaiting`); a peer that exits leaves a harness notice instead (`Store::abandon`). `MAX_SENT` per ten minutes stops answer loops. Awareness: every Claude and Codex launch is told about its peers with the same text. `PEER_NOTE` (short) goes into Claude's `--append-system-prompt`, Codex's `-c developer_instructions=` (skipped when the operator's own `config.toml` sets that key) and the `mcr` server's MCP instructions; it must hold no quotes, as it is put into a shell word and a TOML string. The working rules are `PEER_GUIDE` (peers) and `REPORT_GUIDE` (reports and the bulletin board), served twice: as the Claude skills `agent-mcr:peers` and `agent-mcr:reporting` from `<config dir>/claude-plugin`, loaded with `--plugin-dir` for the launch only, and together as the `guide` tool for every agent kind. A test checks that every tool the note names exists and is explained. A resumed Claude conversation keeps its recorded system prompt, so there the note arrives through the MCP instructions and the skill. Sessions without the MCP tools: `Tracked.tools` is set when a session's `mcr` bridge first connects. For a session without it (started before the tools existed, or an agent that takes no MCP servers) `nudge` types a notice that gives the command form instead: `agent-mcr --harness-tool <name> [json]` (`tool_cli`), the same tools with the same `caller` identity check, printing JSON. Names: a session nobody named goes by the title its agent set in the terminal (`title_name`: without the status glyph and Codex's ` | folder` suffix; empty when it is only the agent's or folder's name). `sessions` keeps it in `Tracked.title` and reports it as `harness.name` with `named: false`, so the list, `list_peers`, addressing by name and message senders agree. `AgentMark.tsx` draws the agent kind as a small mark (simplified, not the vendors' artwork). The supervisor is not a list row: it has its own tile above the form. Supervisor session: the `supervisor` control op (app command `harness_supervisor`, the button at the top of the Live list) returns the running session with `meta.role = supervisor` or starts one: Claude in `<config dir>/supervisor`, with `claude-supervisor-mcp.json` (the `mcr` and `supervisor` servers) and `claude-supervisor-hooks.json` (both allowed without prompts, D5). The role can't be set through `create` or `session_create`. `supervise` refuses hosted sessions that are not the supervisor (`caller`), so a worker can't take over the harness; agents outside the harness keep the tools. D6 still holds for the supervisor session. The first start asks whether to trust the folder; only the person answers. Subagents: `subagents` lists a Claude session's subagents from the files next to its transcript (`<session id>/subagents/agent-<id>.jsonl` and `.meta.json`), reading only the meta file and modification times, never transcript text, and only under `~/.claude/projects`. `sessions` attaches those active in the last hour; the Live list shows them as rows under the session, marked active when written to in the last 90 s (file activity, not verified liveness). `subagent_finished` looks at the last transcript record only (a final assistant message, or the report acknowledgement, whose wording depends on the Claude Code version); finished ones are counted in one line, not listed. Codex subagents (`codex_subagents`) are the rollout files whose head names the session's thread as `parent_thread_id`; they are named by the last part of `agent_path`, with Codex's nickname as the kind, and count as finished when the last record is `task_complete` or `turn_aborted`. Both go through `Adapter::subagents`, cached five seconds per session. Bridges: `--harness-mcp` and `--supervise` go through `bridge`, which outlives a service restart (every rebuild restarts it): it reconnects, replays the client's `initialize` and `notifications/initialized` without passing the second answer on, and answers the calls that were in flight with an error. A plain pipe here makes every running agent drop the server for good. Terminal size: `TerminalPane` fits only after the pane's size has been still for `RESIZE_SETTLE_MS`, because each new size makes Claude Code and Codex repaint their whole transcript. Three more rules, each from a flicker that came back: the element xterm is fitted to (`.hs-terminal`) has no padding and `contain: strict`, because the fit reads its border-box height and anything spilling out of the Live view makes the scrolling Sessions area show a scroll bar that resizes the terminal again (the gap lives on `.hs-terminal-pad`); sizes go to the runner one at a time, newest last (`sendSize`), because two requests in flight can land in the wrong order and leave the agent drawing for another width than the screen's; and a pane that is shown again sends its size even when it did not change. Live list: a row is the state dot, the agent mark, name and folder; a second line appears only for tasks, unread messages, a prompt or the agent's own status. Pid, command and state text are in the tooltip. Idle and ended rows are dimmed. Each row has one action menu (`RowMenu`): Copy reference (`sessionReference`, text to paste into another session) and Close session, which hangs the session up and forgets it once it has ended (`closing`); there is no interrupt button. `sessions` reports `peers` (`Store::talked_with`: live sessions with a message either way in the last day) which the row tooltip names (the list itself is sectioned by folder, see Folders). Each terminal pane is headed by the name its session has in the list (`.hs-pane-title`). Finished subagents are not shown. `Tracked.tools` follows the connected bridges (`Store.bridges`, reset when the service starts), so a session whose bridge is gone gets the command form in notices. Agent adapters: `agents.rs` holds one `Adapter` per agent program (`Claude`, `Codex`, `Antigravity`, `Shell`) and everything specific to it: the command line for a launch and a resume, the files a launch reads (`files`, written before every launch), whether the harness names the conversation, how it reports (`reports_from_start`, `silent_until_first_turn`, `at_prompt`), how a turn is stopped (`interrupt`), whether the peers note fits (`takes_note`) and where its transcripts are. `harness.rs` asks `adapter(profile)` and must not compare profile names; an unknown profile is a shell. A new agent is a new adapter plus a `PROFILES` entry. `Antigravity` (`agy`) has no hooks, MCP tools or transcripts yet, so `is_agent` is false: it is a terminal with no state, takes no task (`session_create` refuses one). Agents without state tracking (Antigravity, OpenCode, Pi) get inbox notices only when their adapter's `at_prompt` sees the input box (default false: nothing is typed into a menu; only Antigravity has markers so far). `terminal_write` takes `submit` (Enter as a separate write 250 ms after the text, `submit_writes`, shared with tasks and notices); a trailing literal `\r`/`\n` counts as submit. Restart: the `restart` control op (app command `harness_restart`, the row menu, supervisor tool `session_restart`) hangs the agent up, waits for the exit and starts a new process that resumes the same conversation (`Tracked.agent_session`, only if `find_resumable` finds its transcript; otherwise a fresh start in the same folder, `resumed: false`). The session id changes: name, role, queued tasks, messages and status move to the new one and the old row is forgotten. `Store.restarting` keeps the exit from failing queued tasks or telling askers the peer left. The tool refuses in the middle of a turn without `force`; the menu forces. It must answer within the control client's ten seconds. Usage pane: the Usage button in a terminal's title opens `SessionStats.tsx` beside the terminal (open or closed is kept in localStorage). It asks `session_stats` (same grant as the Sessions workspace, no transcript text) for the session whose id is the hosted session's `agentSession`; figures are never self-reported by agents. `sessions::Context` is filled by the same parser as usage (`PARSER_VERSION` 4): `now`/`first`/`peak` are the input side of a model response (Claude: main chain only; Codex: `last_token_usage`, with `model_context_window` as `window`), `compactions`, `tool_bytes` (bytes each tool returned, matched by call id through `Indexed.calls`) and `skills` (explicit invocations only). Tool output is shown in bytes because transcripts record no tokens per tool; do not convert it to tokens. Running shells: `sessions` adds `shells` to each live agent session, the `sh -c` processes among the descendants of its pid (`shells`, from `ps` through `process_table`, cached two seconds), named by the command they run. This is the process table, so it is verified liveness, unlike subagents. MCP servers and the bridge are not shells and are not listed. The Live list shows them under the row, and a session with a running shell is not dimmed even when idle. Each shell carries the processor time of its whole process tree, whether a process in it is suspended, and `quietSince`: when the service last saw that processor time move (`with_activity`, a map kept in the service, so it starts over at a service restart and only advances while something asks for the session list). The list shows a shell as quiet after `SHELL_QUIET_MS` without processor use. Quiet is not stuck: a command waiting on the network, a lock or a sleep looks the same, and the wording must keep saying so. Folders: the Live list is sectioned by working folder (`directorySections`): folders with at least one running session first, then the rest (added ones, kept in localStorage `hs-dirs`, and ones that only have history), each group sorted by path. The order must not depend on state: a session that starts waiting is marked, never moved, and rows inside a folder stay in start order. A section is a left bracket and a top line with the folder's path set into it (`.hs-dir`, `shortPath`); the same line has one "+" whose menu starts Claude or Codex in that folder (`RowMenu`, also the row's "…"; no shell there) and a search button for the folder's history. There is no separate start form. Under its sessions a folder lists its earlier conversations (`Resumable`, two weeks back, titles from the Sessions index when access is on) and one click resumes one there. Sessions are no longer grouped by messages; who a session talks to is in its tooltip. The second view is Journal (`view` is still stored as `history`): `SessionResults.tsx` lists matches by folder in the same section shape, `SessionTree` rows are two lines, filters sit in a disclosure above the results, and a session's detail offers Resume in Live. Not built yet: MCP Tasks for `ask`/`listen` (both are plain tool calls), groups (D9: peers are all sessions), `declare_dependency`, a messages view in the app.

Supervisors and executors (decision D15, MCR-41): `Tracked.supervisor` is the id of the session a session works for; `Harness::restart` carries it to the new id, and `Store::drop_dangling` (run on every update) makes executors independent when their supervisor is gone. Nothing restores a relation by itself. `Store::bind` is the one place that sets it: no self, no circle, at most `MAX_DEPTH` levels and `MAX_EXECUTORS` per session. A relation is made by the operator (`harness_spawn` with `supervisor`, `harness_bind` after a native dialog), by the root Supervisor for a session it creates (`session_create(supervisor)`) or by a hosted agent for itself (`executor_create`, in its own folder or below). Never hold the store's lock in an `if let` or `match` scrutinee around a call to `update`: the mutex is not re-entrant and the service hangs. The task tools of the mcr server (`task_assign`, `task_status`, `task_wait`, `session_status`, `session_result`, `terminal_read`) first check `Harness::mine` / `Store::under`: a session reaches its executors and theirs, never another session; there is no `terminal_write` for it, and D6 holds. `Task.by` names the assigning session and is set from the caller's process, never from tool arguments; `tell_assigners` puts the outcome in its inbox, and `report` also posts to the supervisor's inbox. Waits (MCR-41, part two): `Store.waits` holds what sessions registered with `wait_register`; `Harness::escalate_waits`, on the service's three-second timer, tells the session's supervisor (or the root Supervisor) when a wait runs past its time and, after as long again, raises attention for the operator; `wait_resolve` is for a supervisor above the waiting session. `Tracked.created_by` is set only by `executor_create`, and `executor_end` ends only such an executor that is idle, still works for the caller and has no executors of its own (MCR-46). In the list, `relationRows` (`utils/harness.ts`) orders one folder as trees; an executor whose supervisor is in another folder stays in its own folder and names it.

Slack connector (`slack.rs`, decision D14, epic MCR-26; design and its "What is built" table in `docs/AGENT_HARNESS_DESIGN.md`): part of the harness service, never of the runner or the app. It holds one Socket Mode connection (`tungstenite`) and calls Slack's Web API with form POSTs (`ureq`). The bot and app-level tokens live only in the macOS Keychain (`Vault`, service `cc.lambdahouse.agent-mcr.slack`): never put them in `slack-state.json`, a status, a tool result, a log line or the audit. `slack-state.json` holds the connection record, channel policies, received messages, posts and the audit; every change is written before it is acted on. Invariants, each with a test in `slack.rs`: a message reaches a session only from a sender on the channel's list, once, as inbox data (`Message.slack`), never typed into a terminal; a post is sent only in state `approved` with `allowed_by` set, by the channel's policy, the app (`slack_decide`) or a Slack button pressed by the recorded operator for the stored text hash; a post is sent at most once (`sending` → `unknown` → looked up in the channel's history, never retried); agent text is escaped and shown in `plain_text` blocks or with `verbatim: true`, so it mentions nobody. Only `control` (the app) changes policies or decides; the supervisor has `slack_status` and nothing else. The app's commands (`slack_*` in `harness_commands.rs`) ask in a native dialog before connecting, before a policy that posts without approval, and before another person's messages may reach an agent. `Slack` talks to the rest of the service through the `Host` trait and to Slack through `Web`, both faked in tests; `SlackView.tsx` is the panel. The app manifest for the Slack app is `docs/slack-app-manifest.yaml`.

### Sessions workspace

`SessionWorkspace.tsx` is entered from the toolbar. `utils/sessions.ts` defines its IPC contract and pure accounting/search helpers. `src-tauri/src/sessions.rs` is the incremental Codex/Claude JSONL index, backed by `session_db.rs` (SQLx SQLite) and versioned checkpoints plus paged events. All database work runs on blocking workers. Checkpoints and events commit atomically; usage deduplication survives restart. Do not discard history when directory enumeration fails. `session_memory.rs` discovers fixed memory locations and revalidates each read; `Access.session_memories` is a separate native grant. Human forks are not child agents. Directory history, role and last-activity filters are defined in `utils/sessions.ts`; `session_commands.rs` holds the opt-in access gate. There is no control of sessions outside the harness: the "direct" tab and `session_control` (Codex's own daemon socket) are removed, and the harness is the only way to type into an agent. The app holds no third-party credentials and fetches nothing from outside services (MCR-24): ticket keys found in transcripts are shown as text; do not add a network client for them. `Access.session_workspace` is independent of `agent_workspace`. Do not grant general document reads for transcripts. Usage records must be deduplicated; cache/reasoning are subsets of input/output, not extra totals. Summaries exclude activity bodies, and details load on selection. Status inferred from files must not be presented as verified process liveness. Tests cover parser accounting, partial/truncated files, hierarchy and the UI access/control paths. `examples/session_snapshot.rs` extracts real local metadata using the same index.

Memory reader windows use a validated `memoryDocument` URL and isolated, read-only inherited preferences. They do not overwrite the main workspace, own its watchers or consume its launch paths. Native menu events target the focused window.

### Session analysis MCP

`session_analysis.rs` is the bounded read-only query layer; `session_mcp.rs` implements MCP lifecycle, the app-owned Unix socket and the `--mcp` stdio bridge. The bridge branch in `main` must run before AppKit/Tauri initialization and never open SQLite. `session_analysis_commands.rs` owns the per-process native-confirmed grant and background ingestion using the same `SessionState.index` as the UI. Revocation closes connected sockets; keep grant→index lock order. `SessionAgentAccess.tsx` shows scope, clients, query audit and evidence navigation. Never infer inner exec execution, skill success, historical definition versions or per-tool tokens from references. `examples/analysis_host.rs` and `scripts/validate-session-mcp.mjs` exercise the production query/transport with the official MCP client SDK and explicit fixture paths. See `docs/SESSION_ANALYSIS_MCP.md` for semantics and remaining limits.

### Path Alias

TypeScript path alias `@/*` maps to `src/*` (configured in tsconfig.json and vite.config.ts).

## Configuration

There is no config file. UI settings, folders, tabs and workspaces live in localStorage (Zustand persist). The backend's config dir (`dirs::config_dir()/agent-mcr`) holds `access.json`, `history/history.md`, `read-state/` (agent workspace), and `sessions/index.sqlite` with its SQLite sidecars. Revoking session access clears the SQLite index and disables memory access.

## Key Patterns

- React functional components with hooks (no class components except ErrorBoundary)
- CSS custom properties for theming: dark by default, light overrides under `:root[data-theme='light']`; Shiki emits both themes as `--shiki-dark` / `--shiki-light` variables
- Zustand actions return `{ success: boolean; error?: string }` for operations that can fail
- Scroll handlers debounced at 50ms
- Mermaid renders lazily with strict security level
